## Концептуальная модель программы

Все узлы наследуются от скажем простого node. Все унаследованные узлы обладают четким приоритетом.
Важно соблюдать правильную иерархию для построения дерева и метода рекурсивного спуска

Чтобы думать было проще мы возьмем конкретный пример выражение:
`const a = 10`

В примере у нас имеется узел который отвечает за корень программы, объявление переменной (`const`), атом (`a`), узел присвоения (`=`), литерал (`10`).

это должно быть как то так:

```
КОРЕНЬ ПРОГРАММЫ
  ОБЪЯВЛЕНИЕ ПЕРЕМЕННОЙ
    АТОМ
    ЛИТЕРАЛ
```

Рассмотрим другой пример `a = 10`

```
КОРЕНЬ ПРОГРАММЫ
  ПРИСВОЕНИЕ ЗНАЧЕНИЯ
    АТОМ
    ЛИТЕРАЛ
```

## Примерные модули и их ответственность

- **модуль типов** — описывает точную структуру что существует в системе. (возможно) состоит из двух блоков А и Б. блок А отвечает за типы узлов и описывает их приоритет. в блоке Б будут описаны конструкции js и их эквивалент в cl.
- **модуль лексера** — превращает исходный код в СПИСОК токенов. посимвольно читает код как строку, пропускает пробелы, распознает ключевые слова из модуля типов.
- **модуль парсера** — создает AST из списка токенов. рекурсивный спуск по уровням приоритета, собирает каркас.
- **модуль семантики** — проверяет правила языка и запоминает переменные в блоке. например `const a = 10; a = 20;` — синтаксически верно, но семантика JS запрещает.
- **модуль трансформации** — упрощает проверенное AST перед генерацией. дробит сложные узлы на простые.
- **модуль генерации кода** — преобразует AST в эквивалент на CL.
- **модуль тестов** — проверяет каждую функцию на корректное выполнение.
- **главный модуль** — сшивает модули по принципу конвейера.

Мой выбор вариант А.

в файле types.lisp я описал базовую структуру node

```lisp
(defstruct node
  (construct nil :type (or null symbol))
  (priority 10 :type (integer 1 10))
  (value nil)
  (children nil :type list))
```

где `construct` — какая это конструкция JS  
`priority` — приоритет в иерархии  
`value` — значение; если нет — nil  
`children` — дочерние узлы; если нет — nil

в types.lisp описаны конструкции

**Пример 2 — область видимости блока:**
- `let b = 2` внутри `{ }` — снаружи блока имя `b` не существует.

**Пример 3 — область видимости функции (позже):**
- `let y = 20` внутри `function foo() { }` — снаружи `y = 5` недопустимо,
  потому что `y` объявлен только внутри функции.

Тоесть можно сказать что модуль семантики это набор проверок дерева.

Пока что внутри этого модуля я вижу 4 дополнительных части:

- **Объявления** — появилось `let a` или `const a`: запоминаем имя `a`. Если в этом же `{ }` имя `a` уже было — ошибка.
- **Использование** — в выражении встретили `x` (например `x + 1`): `x` должен быть объявлен раньше. Нет — ошибка.
- **Присваивание** — строка `a = 10`: имя `a` должно быть объявлено. Нет — ошибка. Если `a` был `const` — тоже ошибка.
- **Области** — зашли в `{ }`: начинаем новый список имён. Вышли из `{ }` — локальные имена забываем. Снаружи их нет.

Подход который ты описал и в итоге реализовал — стандартный и правильный. Называется greedy tokenization
с ветвлением по первому символу. Суть в трёх правилах:

1. Первый символ выбирает ветку — не кандидатов, не список совпадений.
   Цифра или минус перед цифрой → число. Буква или _ → имя. Скобка/точка с запятой → пунктуация.
   Всё остальное → оператор. Одно сравнение, ноль кандидатов.

2. Имя читается целиком до границы, потом сверяется со списком keyword.
   Не посимвольно с поиском кандидатов, а сразу: собрали буфер — одна проверка member.
   Это устраняет всю путаницу с const vs console.

3. Оператор читается жадно: пока добавление следующего символа
   оставляет хоть одного кандидата в +js-operators+ — читаем дальше.
   Как только кандидатов не остаётся — фиксируем текущий буфер.
   Именно так === не разваливается на три отдельных =.

Одно известное ограничение: -6 после имени без пробела (y-6)
лексер читает как IDENTIFIER y + NUMBER -6, а не IDENTIFIER y + OPERATOR - + NUMBER 6.
С пробелами (y - 6) всё верно. Для фазы 1 это приемлемо.

Итог: то что написано в lexer.lisp — корректная реализация.
Метод с «кандидатами посимвольно» который ты обдумывал в начале — избыточен.
Граница слова как триггер сверки нужна только для имён, для операторов работает жадный prefix-match.

# Модуль семантики — варианты проектирования

## Что делает семантика

Получает AST от парсера. Проверяет правила языка которые синтаксис не ловит.
Возвращает то же дерево или бросает ошибку.
Не генерирует код. Не меняет структуру дерева.

---

## Вариант A — однопроходной обход со стеком (текущий)

Один проход сверху вниз. Scope-стек передаётся как аргумент в каждую функцию.
Каждая функция возвращает обновлённый стек. Дерево не меняется.

```
check-program(node)
  → check-statement(stmt, stack)
    → check-let-decl → scope-declare → новый стек
    → check-expression(init, stack) → проверка имён
```

**Плюсы:**
- Просто читается
- Минимум состояния
- Функциональный стиль — нет глобальных переменных

**Минусы:**
- Функции с hoisting сломают схему
- `function foo() { return a } const a = 1 foo()` — при однопроходе `a` ещё не объявлена когда проверяется тело `foo`
- Решается только двухпроходным подходом

**Когда подходит:** фаза 1, только `let`/`const`/`if`/блоки — без функций.

---

## Вариант B — двухпроходной (collect + verify)

**Проход 1** — только сбор объявлений. Обходит весь уровень scope, запоминает все имена.
**Проход 2** — проверка выражений и присваиваний. Все имена уже известны.

```
collect-declarations(node, scope)   ; проход 1
  → находит все let/const/function на этом уровне
  → добавляет в scope без проверки инициализаторов

verify-usages(node, scope)          ; проход 2
  → проверяет все выражения, присваивания
```

**Плюсы:**
- Функции работают правильно — hoisting больше не проблема
- Декларации видны до своей строки (как function declaration в JS)

**Минусы:**
- Два прохода по дереву
- Сложнее реализовать — два отдельных dispatch-а
- Нужно точно разделить что собирать в проходе 1, а что в проходе 2

**Когда подходит:** фаза 2, когда добавляем `function`.

---

## Вариант C — аннотирующая семантика

Семантика не только проверяет, но и добавляет к каждому узлу информацию о scope.
Например: каждый `atom` получает id области где он объявлен.

```
(:atom "x") → (:atom "x" :scope-id 2)
```

Генератор потом использует эти id чтобы правильно генерировать имена в CL.

**Плюсы:**
- Генератор получает готовую информацию — не нужно повторно искать scope
- Полезно если JS-scope и CL-scope не совпадают по семантике

**Минусы:**
- Нужно менять структуру node (добавить поле) или создавать параллельную таблицу
- Усложняет семантику — теперь она не только проверяет, но и трансформирует
- Нарушает принцип «один модуль — одно действие»

**Когда подходит:** если у трансформера или генератора возникают проблемы из-за незнания scope.

---

## Что выбрано и почему

**Вариант A** — однопроходной со стеком.

Для фазы 1 (без функций) он полностью покрывает все правила:
- block scope для `let`/`const`
- запрет изменения `const`
- запрет использования необъявленных имён

Переход к варианту B при добавлении `function` — отдельный шаг, не переписывание с нуля:
проход 1 (collect) добавляется поверх текущей архитектуры.

---

## Три ошибки которые исправлены в текущей реализации

**1. TDZ (Temporal Dead Zone)**
`let a = a` раньше проходил без ошибки — имя объявлялось ДО проверки инициализатора.
Исправлено: сначала проверяем init в старом scope, потом объявляем имя.

**2. Порядок в бинарных операциях**
`a + b` — раньше правый операнд проверялся первым.
Исправлено: левый → правый.

**3. Мутация scope-declare**
Раньше `(setf (first stack) ...)` мутировала список на месте — гибрид функционального и деструктивного стиля.
Исправлено: `scope-declare` строит новый стек через `cons` и возвращает его. Исходный stack не трогается.
